> وضعیت: **تأییدشده و ساخته‌شده** — تاریخ تصویب: ۲۰۲۶-۱۱-۲۰
>
> هدف: افزایش سرعت ساخت، توسعه، تست و پژوهش با تقسیم کار میان چند زیرایجنت تخصصی، بدون به‌هم‌ریختن مرزهای امنیتی و مالکیت فایل‌ها.
>
> فایل‌های ایجنت در `.opencode/agents/` ساخته شده‌اند و frontmatter آن‌ها با YAML اعتبارسنجی شد.

## ۱. خلاصهٔ اجرایی

پیشنهاد می‌شود ۶ زیرایجنت هسته و ۲ زیرایجنت اختیاری ساخته شوند. ایجنت اصلی (همین نشست) نقش **هماهنگ‌کننده** را دارد و تنها کسی است که:

- دامنهٔ هر کار را تعیین می‌کند،
- قرارداد API را قبل از موازی‌سازی قفل می‌کند،
- خروجی زیرایجنت‌ها را بازبینی و ادغام می‌کند،
- دروازهٔ نهایی کیفیت را اجرا می‌کند.

زیرایجنت‌ها در نشست‌های فرزند با **context تازه** اجرا می‌شوند؛ بنابراین هر بار یک «بریف» کامل و خودکفا دریافت می‌کنند. این ویژگی هم مزیت است (تمرکز و عدم آلودگی context) و هم ریسک (انحراف از تصمیم‌های قبلی) — که با بریف استاندارد و مالکیت مسیرها کنترل می‌شود.

**نتیجهٔ مورد انتظار:** کاهش ۳۰ تا ۳۵ درصدی زمان تقویمی هر فاز، به قیمت ۱۰ تا ۱۵ درصد هزینهٔ هماهنگی و بازبینی.

## ۲. چرا زیرایجنت، و چرا نه بیشتر از این؟

### مزیت‌های واقعی در این مخزن

| مزیت | توضیح |
|---|---|
| موازی‌سازی واقعی | بک‌اند، فرانت و تست سه جریان مستقل‌اند و با قرارداد ثابت می‌توانند هم‌زمان پیش بروند. |
| جداسازی context | هر زیرایجنت فقط فایل‌های دامنهٔ خود را می‌خواند؛ مصرف توکن و خطای تمرکز کم می‌شود. |
| تخصص | قواعد امنیتی، مقیاس تایپ، RTL و تست هرکدام به یک نقش ثابت سپرده می‌شوند. |
| بازبینی مستقل | زیرایجنت امنیت، تغییرات را بدون تعصب نویسنده بررسی می‌کند. |
| پژوهش موازی | پژوهش روند/رقبا هم‌زمان با توسعه اجرا می‌شود و مسیر را مسدود نمی‌کند. |

### محدودیت‌هایی که طرح را تعیین می‌کنند

1. **context تازه:** زیرایجنت هیچ‌چیز از این گفتگو نمی‌داند. بریف باید شامل هدف، غیرهدف، مسیرهای مجاز، قرارداد، معیار پذیرش و دستورهای تست باشد.
2. **هم‌زمانی روی یک Working Tree:** دو نویسنده روی یک فایل = تعارض. مالکیت مسیر اجباری است.
3. **گزارش خودادعایی بی‌ارزش است:** هر «انجام شد» باید با خروجی دستور و exit code همراه باشد.
4. **هزینه:** هر زیرایجنت یک نشست کامل است. برای کارهای کوچک (کمتر از ~۳۰ دقیقه) خودِ ایجنت اصلی سریع‌تر است.

**قاعدهٔ طلایی:** زیرایجنت فقط وقتی ساخته می‌شود که یک جریان کاری تکرارشدنی و قابل‌مرزبندی داشته باشد؛ نه برای هر فایل.

## ۳. نقشهٔ نقش‌ها

### ۳.۱ هستهٔ پیشنهادی (۶ نقش)

| # | شناسه | مسئولیت | مالک نوشتن | خروجی اصلی |
|---|---|---|---|---|
| ۱ | `backend-dev` | API، سرویس، اسکیمای Pydantic، مدل داده، منطق مجوز در سطح endpoint | `app/**` | کد + گزارش تست هدفمند |
| ۲ | `frontend-dev` | UI فارسی/RTL، کامپوننت، context، کلاینت API، دسترس‌پذیری | `webapp/src/**` به‌جز تست‌ها | کد + lint/build |
| ۳ | `test-author` | تست واحد/API/DOM، fixture، پوشش منفی و نقش‌محور | `tests/**`، `webapp/src/**/*.test.*`، `webapp/scripts/dom-tests/**` | تست‌های جدید + نتیجهٔ اجرا |
| ۴ | `security-reviewer` | بازبینی IDOR، دورزدن مجوز، افشای راز/PII، کامل‌بودن audit | هیچ (فقط‌خواندنی) | یافته‌ها به ترتیب شدت |
| ۵ | `docs-writer` | همگام‌سازی `docs/`، README، CHANGELOG، PROJECT_STATUS | `docs/**` به‌جز `docs/research/**`، `README.md`، `CHANGELOG.md`، `PROJECT_STATUS.md` | مستند به‌روز |
| ۶ | `trend-researcher` | پژوهش روندهای ۲۰۲۶، الگوهای UX، رقبا، راهکارهای فنی | `docs/research/**` | یادداشت پژوهش + گزینه‌های قابل‌اقتباس |

### ۳.۲ اختیاری (در صورت تأیید)

| # | شناسه | مسئولیت | چرا اختیاری |
|---|---|---|---|
| ۷ | `db-guardian` | بازبینی طرح مهاجرت SQLite، سازگاری عقب‌رو، برنامهٔ rollback؛ فقط‌خواندنی | فقط در فاز ۳ (`token_version`/`user_sessions`) ارزش دارد. |
| ۸ | `release-verifier` | اجرای کامل دروازهٔ کیفیت و دسته‌بندی شکست‌ها؛ فقط‌خواندنی | ایجنت اصلی هم می‌تواند اجرا کند؛ صرفه‌جویی وقتی زیاد است که تست‌ها طولانی شوند. |

### ۳.۳ چرا `explore` سفارشی نساختیم؟

ابزار داخلی `explore` برای جست‌وجوی سریع کافی است. ساخت نسخهٔ دوم، فقط توکن و نگهداری اضافه می‌کند. جست‌وجوی «کجا این تابع صدا زده می‌شود؟» به `explore` می‌رود؛ تحلیل اثر و طراحی به `trend-researcher` یا خودِ هماهنگ‌کننده.

## ۵. پیاده‌سازی در OpenCode

### ۵.۱ محل و قالب

فایل‌ها در `.opencode/agents/<name>.md` ساخته می‌شوند. بدنهٔ Markdown همان system prompt است و frontmatter شامل `description`، `mode: subagent`، `permissions` و `steps` است.

نمونهٔ کامل برای `backend-dev`:

```md
---
description: پیاده‌سازی API، سرویس و مدل بک‌اند؛ بدون ویرایش فرانت و تست
mode: subagent
steps: 30
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: edit
    resource: "app/**"
    effect: allow
  - action: edit
    resource: ".env*"
    effect: deny
  - action: edit
    resource: "*.db"
    effect: deny
  - action: subagent
    resource: "*"
    effect: deny
  - action: shell
    resource: "*"
    effect: ask
  - action: shell
    resource: ".venv/Scripts/python.exe -m pytest*"
    effect: allow
  - action: shell
    resource: "ruff check*"
    effect: allow
  - action: shell
    resource: "git status*"
    effect: allow
  - action: shell
    resource: "git diff*"
    effect: allow
  - action: shell
    resource: "git commit*"
    effect: deny
  - action: shell
    resource: "git push*"
    effect: deny
---
You are the backend developer for a FastAPI + SQLAlchemy async + SQLite clinic system.

Hard rules:
- Only edit files under app/. Never edit tests/, webapp/, docs/, .env, or *.db.
- Preserve the centralized permission model in app/auth/permissions.py; never bypass authorize_tool_call.
- Keep Persian user-facing messages; keep code and comments in English.
- Run targeted pytest and ruff after changes. Report the exact commands and exit codes.
- Never commit, push, install dependencies, or modify database files.
- If a contract change is required, stop and report it instead of editing another owner's files.

Report to the parent in Persian using the standard report format.
```

### ۵.۲ جدول مجوزها

| ایجنت | edit | shell | subagent | web |
|---|---|---|---|---|
| `backend-dev` | فقط `app/**` | تست/ruff/git خواندنی allow؛ بقیه ask | deny | deny |
| `frontend-dev` | فقط `webapp/src/**` منهای تست‌ها | lint/build/test allow؛ بقیه ask | deny | deny |
| `test-author` | `tests/**` + فایل‌های تست | اجرای تست allow | deny | deny |
| `security-reviewer` | deny | فقط دستورهای خواندنی/تست | deny | deny |
| `docs-writer` | فقط مسیرهای مستند | خواندن/جست‌وجو | deny | allow |
| `trend-researcher` | فقط `docs/research/**` | خواندن | deny | allow |
| `db-guardian` | deny | فقط خواندن | deny | deny |
| `release-verifier` | deny | اجرای دروازهٔ کیفیت | deny | deny |

نکته‌های اجرایی:

- **آخرین قاعدهٔ منطبق برنده است**؛ قاعده‌های کلی قبل از استثناها می‌آیند.
- `effect: ask` در زیرایجنتِ پس‌زمینه ممکن است منتظر تأیید بماند؛ به همین دلیل دستورهای پرتکرار صریحاً `allow` می‌شوند و فقط دستورهای ناشناخته `ask` می‌مانند.
- `hidden: true` فقط نمایش را پنهان می‌کند و ابزار امنیتی نیست؛ امنیت از `permissions` می‌آید.
- برای هر زیرایجنت `subagent: deny` می‌گذاریم تا زنجیرهٔ بازگشتی ایجاد نشود.
- **مدل:** فعلاً ارث‌بری از ایجنت اصلی. اگر بخواهید، در فاز ۰ مدل ارزان‌تر برای پژوهش/مستندات و مدل قوی‌تر برای کد تعیین می‌شود؛ انتخاب مدل بدون تأیید شما انجام نمی‌شود.

## ۶. پروتکل بریف و تحویل

### ۶.۱ بریف اجباری (هماهنگ‌کننده → زیرایجنت)

```md
## هدف
یک جملهٔ قابل‌سنجش.

## غیرهدف
کارهایی که در این مأموریت انجام نمی‌شود.

## دامنهٔ فایل
مسیرهای مجاز + مسیرهای ممنوع.

## قرارداد
امضاهای API/تایپ/رویداد که نباید تغییر کند.

## معیار پذیرش
- رفتاری
- تستی
- امنیتی

## دستورهای تأیید
دستورهای دقیق تست/lint/build و انتظار خروجی.

## زمینهٔ لازم
تصمیم‌های قبلی، نام‌های دقیق (`queue_number`, `APPOINTMENT_SLOT_IN_PAST`, …)، و محدودیت‌ها.
```

### ۶.۲ قالب گزارش (زیرایجنت → هماهنگ‌کننده)

```md
## وضعیت
DONE | PARTIAL | BLOCKED

## تغییرات
- مسیر — چه چیزی و چرا

## دستورها
- `...` → exit 0 / FAIL (خلاصهٔ خطا)

## تصمیم‌ها و مفروضات
...

## ریسک / باقی‌مانده
...

## پیشنهاد گام بعد
...
```

**بدون خروجی دستور، وضعیت DONE پذیرفته نمی‌شود.**

## ۷. جریان کار روی فازهای سند ۱۴

| فاز توسعه (سند ۱۴) | زیرایجنت‌ها | الگوی اجرا |
|---|---|---|
| ۰ — تأیید طرح، توکن‌ها و متن‌ها | `trend-researcher` + `docs-writer` + `frontend-dev` | موازی (مسیرها جدا) |
| ۱ — وضعیت/سلامت سامانه | `backend-dev` → `frontend-dev` → `test-author` → `security-reviewer` → `docs-writer` | بک‌اند اول؛ فرانت و تست پس از قفل قرارداد |
| ۲ — مرکز حساب کاربری | `backend-dev` → (`frontend-dev` ∥ `test-author`) → `security-reviewer` → `docs-writer` | قرارداد اول، سپس موازی |
| ۳ — امنیت حساب و نشست | `db-guardian` (طرح) → `backend-dev` → `frontend-dev` → `test-author` → `security-reviewer` | سریال (تغییر مدل داده) |
| ۴ — پیشنهادهای زمینه‌مند | `backend-dev` → (`frontend-dev` ∥ `test-author`)، `trend-researcher` موازی | پژوهش موازی، کد پس از قواعد |
| ۵ — رتبه‌بندی LLM | `backend-dev` + `test-author` | سریال/کوتاه |
| ۶ — انتشار و مستندسازی | `release-verifier` + `docs-writer` | موازی |

**قاعدهٔ موازی‌سازی:** فقط وقتی دو نویسنده هم‌زمان اجرا می‌شوند که مجموعه مسیرهایشان اشتراک نداشته باشد. در غیر این صورت، سریال با تحویل مرحله‌ای.

**Worktree جداگانه:** برای این پروژه پیشنهاد نمی‌شود؛ به‌دلیل `.venv` و `node_modules` سنگین و نیاز به همگام‌سازی مکرر. فقط اگر یک فاز پرریسک (مثل مهاجرت داده) لازم شد، استفاده می‌شود.

## ۸. دروازهٔ کیفیت

هر فاز قبل از «تمام‌شده» اعلام‌شدن باید این‌ها را با خروجی واقعی پاس کند:

```powershell
.venv\Scripts\python.exe -m ruff check app scripts tests
.venv\Scripts\python.exe -m pytest
cd webapp
npm run lint
npm run test
npm run test:dom
npm run build
```

علاوه بر آن:

- بررسی دستی با `sample.db` (هرگز `dental_agent.db`).
- نبود خطای کنسول مرورگر و بررسی RTL/موبایل برای تغییرات UI.
- تست نقش‌محور: هر چهار نقش (`patient`, `receptionist`, `doctor`, `admin`) و حالت «مجوز override».
- بازبینی `security-reviewer` برای هر تغییری که مسیر `/users`, `/auth`, `/agent`, یا audit را لمس می‌کند.

## ۱۰. ریسک‌ها و کاهش آن‌ها

| ریسک | کاهش |
|---|---|
| تعارض دو نویسنده روی یک فایل | مالکیت مسیر + ممنوعیت ویرایش متقابل + ادغام فقط توسط هماهنگ‌کننده |
| انحراف زیرایجنت از تصمیم‌های قبلی | بریف خودکفا + قرارداد قفل‌شده + گزارش اجباری |

| افشای راز یا آسیب به داده | deny روی `.env` و `*.db`؛ نبود دسترسی نوشتن به `dental_agent.db` |
| هزینهٔ زیاد مدل | مدل ارث‌بری‌شده به‌صورت پیش‌فرض؛ مدل ارزان‌تر برای پژوهش/مستندات پس از تأیید |
| کندی به‌خاطر `ask` | allowlist دستورهای پرتکرار تست/lint/build |
| بازبینی سطحی | `security-reviewer` مستقل + دروازهٔ کامل قبل از تحویل |
| تولید بیش از حد ایجنت | فقط ۶ نقش هسته؛ افزودن نقش جدید نیازمند تأیید |
