# ۱۰. محدودیت‌ها و قابلیت‌های توسعه آینده

## محدودیت‌های فعلی (ثبت‌شده و صریح)

1. **صلاحیت پزشک، نه تشخیص**: دستیار صرفاً coordinator است؛ هیچ‌گونه مشاوره/تشخیص پزشکی نمی‌دهد و برای شکایات حاد پیام ارجاع فوری دارد.
2. **پایگاه داده SQLite**: برای مقیاس کلینیک کوچک منطقی است؛ برای چند نمونهٔ هم‌زمان باید به PostgreSQL مهاجرت شود. محدودکننده‌های نرخ (ورود، OTP، چت، بازخورد) هم درون‌حافظه و مخصوص هر پردازش‌اند و برای چند worker باید به یک مخزن مشترک (مثلاً Redis) منتقل شوند.
3. **تاریخچهٔ چت سمت سرور است** و فقط پیام‌های کاربر/دستیار ذخیره می‌شود (نه بستهٔ ابزارها و نه شناسه‌های داخلی)؛ حذف گفت‌وگو از `DELETE /agent/conversations/{session_id}` انجام می‌شود.
4. **پرداخت و مالی**: خارج از دامنه؛ سرویس‌ها فقط کاتالوگ‌اند.
5. **SMS واقعی**: تأمین‌کننده واقعی (SMS.ir) پیاده شده است (`OTP_PROVIDER=smsir` در `app/auth/sms.py`): دو حالت قالب تأیید/خط خدماتی، فراخوانی async با timeout، fail-closed و بدون لاگ کد/کلید؛ ارسال پس از پاسخ در پس‌زمینه انجام می‌شود (صف/retry و گزارش دلیوری پیامک پیاده نشده است) و خرابی تحویل فقط کد را باطل می‌کند و در لاگ ثبت می‌شود — پاسخ کاربر همیشه یکنواخت می‌ماند. خطای پیکربندی (تأمین‌کنندهٔ ناشناخته یا fake خارج از توسعه) همچنان به‌صورت همزمان با `503` پاسخ می‌دهد. حالت قالب برای OTP توصیه می‌شود (اولویت ارسال بالاتر و بعد از رسیدن به لیست سیاه).
6. **پنل‌های UI**: ایجاد/ویرایش پایه پوشش داده شده ولی برخی ویرایش‌های پیشرفته (مثل ویرایش جزئی برنامه پزشک یا تغییر «فعال/غیرفعال» پزشک/خدمت از رابط) فقط از API (مثلاً `/docs`) ممکن است.
7. **اجرای زنده**: برای ارائه، انتظار می‌رود روی سیستم ارائه‌دهنده به‌صورت محلی اجرا شود؛ وابستگی شبکه فقط هنگام استفاده از ارائه‌دهنده ابری LLM وجود دارد.
8. **یک admin اولیه**: از طریق بوت‌استراپ فقط یک admin اول ساخته می‌شود؛ مدیران بعدی را همان اولین می‌سازد (کنترل اعمال‌شده برای جلوگیری از رقیق‌شدن نقش admin).

## توسعه‌های پیشنهادی آینده

| فوریت | مورد | گروه |
|---|---|---|
| میان | Postgres + Alembic برای مهاجرت‌ها | زیرساخت |
| میان | دستیار Admin/Support (مانیتورینگ خطاها/تعاملات، پاسخ پشتیبانی) | Agent Domain |
| کوتاه | صف ارسال/retry و گزارش دلیوری پیامک OTP روی SMS.ir (فعلاً ارسال مستقیم و بدون صف) | auth |
| میان | book و reschedule از پنل با نمایش معادل شمسی تقویم‌محور | UI |
| کوتاه | اعلان یادآوری نوبت (SMS/ایمیل) | غایب در پروپوزال اما به‌سادگی قابل افزودن روی جدول نوبت‌ها |
| کوتاه | ثبت کاربر عامل ثبت/لغو/جابه‌جایی نوبت در `audit_logs` (اکنون فقط وضعیت و زمان نوبت باقی می‌ماند) | گزارش‌ها |

## چیزهایی که عمداً انجام نشده است

- **پوشش مرورگر واقعی (Playwright/Selenium)**: برای پروژه دانشگاهی، تست‌های DOM جایگزین (jsdom) رفتار رابط را در سطح رشته‌های UI می‌سنجند؛ افزودن Playwright هزینه CI واقعی دارد و از دامنه اصلی پروپوزال خارج است. در صورت درخواست داور قابل افزودن است.

---

> پایبندی به دامنه: هیچ مورد بالا تضاد با پروپوزال ندارد؛ موارد «عمداً انجام‌نشده» در همین سند و docstringهای کد ثبت شده‌اند تا در جلسه دفاع قابل‌پاسخ باشند.

## سخت‌سازی انجام‌شده و محدودیت‌های باقی‌مانده

- سقف صدور OTP (`OTP_PHONE_DAILY_LIMIT`، `OTP_GLOBAL_HOURLY_LIMIT`) از مصرف اعتبار پیامک جلوگیری می‌کند؛ سقف نرخ هر کاربر برای چت و بازخورد (`CHAT_RATE_LIMIT_*`، `FEEDBACK_RATE_LIMIT_*`) هزینهٔ LLM و حجم دیتابیس را محدود می‌کند.
- پیامک OTP پس از ارسال پاسخ در پس‌زمینه تحویل می‌شود؛ بنابراین زمان پاسخ `/auth/otp/request` برای همهٔ شماره‌ها یکنواخت است و وضعیت پاسخ هم در صورت خرابی سرویس‌دهنده تغییر نمی‌کند (کد می‌سوزد و فقط در لاگ ثبت می‌شود). صف با retry و گزارش دلیوری همچنان پیاده نشده است.
- پشت reverse proxy همهٔ کاربران یک IP دیده می‌شوند، چون `X-Forwarded-For` عمداً نادیده گرفته می‌شود؛ قبل از استقرار باید پیکربندی proxy مورد اعتماد اضافه شود.
- توکن‌های JWT مطابق استاندارد `iss`/`aud` را دارند و توکن‌های ورود واقعی به نسخهٔ رمز عبور (دایجست `password_hash`) متصل‌اند؛ بنابراین reset رمز توسط مدیر، همهٔ توکن‌های صادرشدهٔ همان حساب را بلافاصله باطل می‌کند. logout سمت سرور عمومی (لیست نشست‌ها) همچنان وجود ندارد؛ عمر توکن کوتاه (۳۰ دقیقه) است و غیرفعال‌سازی حساب در هر درخواست بررسی می‌شود.
- در محیط production برنامه بدون `JWT_SECRET` و `CONFIRMATION_HMAC_SECRET` قوی و متمایز (حداقل ۳۲ نویسه) شروع نمی‌شود (`app/startup_checks.py`).
