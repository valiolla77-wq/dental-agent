# ۸. راه‌اندازی و اجرای محلی

## پیش‌نیازها

- **Python 3.11+** (توسعه با 3.12 انجام شده)
- برای مدل محلی: [Ollama](https://ollama.com) (اختیاری؛ می‌توانید به‌جای آن از OpenAI/OpenRouter سازگار استفاده کنید)
- Node.js فقط برای اجرای تست‌های UI (اختیاری؛ بخش ۹)

## ۱) ساخت محیط مجازی و نصب وابستگی‌ها

```powershell
git clone <repo-url>; cd dental-agent
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## ۲) تنظیم متغیرهای محیطی

```powershell
Copy-Item .env.example .env
notepad .env
```

کلیدهای ضروری (در `.env`):

| کلید | شرح |
|---|---|
| `JWT_SECRET` | رشته تصادفی مطمئن (برای امضای توکن) |
| `CONFIRMATION_HMAC_SECRET` | رشته تصادفی **مستقل** از JWT_SECRET ( برای تأییدیه‌ها) |
| `AGENT_LLM_PROVIDER` | `ollama` (محلی) یا `openai` / `openrouter` |
| `AGENT_LLM_MODEL` / `AGENT_LLM_BASE_URL` / `AGENT_LLM_TEMPERATURE` | تنظیمات مدل |
| `AGENT_LLM_API_KEY` | فقط برای provider ابری (هرگز commit نشود) |
| `APP_ENV` | `development` برای فعال‌شدن SMS جعلی و `dev_otp`؛ هر مقدار دیگر (شامل `production`) آن‌ها را خاموش می‌کند |
| `OPENROUTER_API_KEY` / `OPENROUTER_HTTP_REFERER` / `OPENROUTER_APP_TITLE` | فقط در حالت OpenRouter |
| `DATABASE_URL` | اختیاری؛ پیش‌فرض `sqlite+aiosqlite:///./dental_agent.db` |
| `SQL_ECHO` | فقط برای دیباگ؛ پیش‌فرض خاموش (لاگ پارامترها داده بیمار دارد) |

## ۳) ایجاد اولین حساب مدیر (بدون رمز در آرگومان/محیط)

```powershell
python -m app.auth.bootstrap_admin
```

اسکریپت تعاملی است: شماره تلفن و رمز را اعلان‌شده می‌خواند (رمز در پاس می‌کاهد) و اگر پیش‌تر مدیری موجود باشد، رد می‌کند. حساب‌های بعدی (پذیرش/پزشک/بیمار) را همان مدیر از درگاه پرسنل (`/staff` ← تب «پرسنل و دسترسی‌ها») می‌سازد.

## ۴) رابط کاربری وب (بستهٔ React جدید)

سامانه دو درگاه جدا دارد:

| درگاه | مسیر | ورود |
|---|---|---|
| درگاه بیماران | `/app` | پیامک یک‌بارمصرف (پیش‌فرض) یا رمز عبور حساب بیمار |
| درگاه پرسنل | `/staff` | فقط رمز عبور — حساب‌های بیمار این‌جا پذیرفته نمی‌شوند |

هر دو صفحه به هم لینک متقابل دارند و سرور هم تفکیک را اعمال می‌کند: ورود با `portal` ناهم‌خوان خطای ۴۰۳ `AUTH_PORTAL_MISMATCH` می‌دهد.

پنل کلینیک از این پس یک اپ React/TypeScript/Tailwind است که در پوشهٔ `webapp/` منبع دارد و FastAPI آن را هم‌دامنه (`same-origin`) سرو می‌کند:

```powershell
cd webapp
npm install        # فقط بار اول
npm run build      # خروجی در webapp/dist با پیشوند /app-assets/
```

| نشانی | شرح |
|---|---|
| <http://127.0.0.1:8000/app> | اپ React (داشبورد، بیماران، نوبت‌ها، پزشکان، چت ایجنت) |
| <http://127.0.0.1:8000/demo> | حذف شده؛ ۴۰۴ برمی‌گرداند |
| <http://127.0.0.1:8000/dev/sms> | سامانه پیامک لوکال (فقط توسعه) |
| <http://127.0.0.1:8000/docs> | مستندات OpenAPI |

- اگر `webapp/dist` هنوز ساخته نشده باشد، `/app` به‌صورت خودکار صفحهٔ قدیمی `web/` را سرو می‌کند تا پروژه همیشه اجراشدنی بماند.
- همهٔ درخواست‌های API همان دامنه (بدون CORS) هستند؛ فرانت پیش‌فرض با URL نسبی کار می‌کند.
- حالت توسعه: `npm run dev` در `webapp/` روی پورت 3000 بالا می‌آید و مسیرهای API را به `:8000` پروکسی می‌کند (`VITE_PROXY_TARGET`).
- آزمون‌های واحد منطق فرانت (RBAC، تاریخ جلالی، تعارض نوبت، زمان‌های خالی): `npm run test` داخل `webapp/`.
- آزمون تعاملی جریان رزرو دستی و «ظاهر محصول» (jsdom، بدون سرور): `npm run test:dom` داخل `webapp/`.
- نام کلینیک در هدر و صفحهٔ ورود: متغیر زمان بیلد `VITE_CLINIC_NAME` (پیش‌فرض: «Dental Agent»؛ نام کلینیک دیگری هرگز پیش‌فرض نیست). فونت وزیرمتن داخل پروژه است و چیزی از اینترنت بارگیری نمی‌شود.

## ۵) اجرای سرور

```powershell
uvicorn app.main:app --reload --port 8000
```

- وب‌سایت نقش‌محور: <http://127.0.0.1:8000/app>
- مستندات OpenAPI: <http://127.0.0.1:8000/docs>

مهاجرت‌های افزایشی و indexهای یکتا در شروع برنامه به‌صورت `lifespan` اعمال می‌شوند (`init_db`).

## ۶) داده نمونه (اختیاری)

```powershell
python scripts\seed_sample.py  # فقط sample.db
python scripts\seed_catalog.py # کاتالوگ واقعی SERVICEها + پزشکان نمونه در دیتابیس فعلی (idempotent)
```

`seed_sample.py` فقط در `sample.db` کار می‌کند و اگر با مسیر دیگر هم بخواهد اجرا شود، صریحاً خطا می‌دهد؛ برای پاک‌کردن داده واقعی طراحی نشده است. `seed_catalog.py` روی همان `DATABASE_URL` اجرا می‌شود، فقط سرویس/پزشک/برنامه اضافه می‌کند (ردیف موجود را بازنویسی نمی‌کند) و تکرارش امن است.

### حساب‌های نمونهٔ محلی

| نقش | شماره | رمز | درگاه ورود |
|---|---|---|---|
| مدیر (سمیرا موسوی) | `09121234500` | `ClinicAdmin!1404` | `/staff` |
| پذیرش (نگین شریفی) | `09121234501` | `ClinicDesk!1404` | `/staff` |
| پزشک (دکتر سارا احمدی) | `09121234502` | `ClinicDoctor!1404` | `/staff` |
| بیمار (نیلوفر احمدی) | `09121234510` | OTP | `/app` |

این اعتبارها فقط برای `sample.db` ساخته می‌شوند و هرگز برای محیط واقعی استفاده نشوند.

## ۷) اتصال حساب پزشک/بیمار به رکورد

پس از ساخت حساب با نقش `doctor`/`patient` توسط مدیر:

- پزشک: درگاه پرسنل ← بخش «پزشکان و شیفت‌ها» → عملیات «اتصال حساب کاربری» (یا API `POST /doctors/{id}/link-user`) با شماره‌ای که روی رکورد پزشک ثبت شده.
- بیمار: درگاه پرسنل ← بخش «بیماران و پرونده‌ها» → عملیات «اتصال به حساب» (یا API `POST /patients/{id}/link-user`) با شماره رکورد بیمار.

پیوند یکتاست و با انطباق شماره انجام می‌شود؛ به این ترتیب هیچ حسابی خودش را متصل نمی‌کند.

## ۸) اتصال مدل زبانی (محلی یا ابری)

- **Ollama** (حالت پیش‌فرض): پس از `ollama pull <model>`، در `.env` مسیر `AGENT_LLM_BASE_URL` را با تنظیمات Ollama بدهید.
- **OpenAI/OpenRouter سازگار**: `AGENT_LLM_API_KEY` را در `.env` (نه در کد) قرار دهید.

اگر مدل تنظیم نشده باشد، سامانه بالا می‌آید ولی هر chat خطای `503 AGENT_PROVIDER_NOT_CONFIGURED` برمی‌گرداند (بخش‌های دیگر کار می‌کنند).

## ۹) پیامک واقعی OTP (SMS.ir)

پیش‌فرض، تأمین‌کننده جعلی است (`OTP_PROVIDER=fake`) که فقط در `APP_ENV=development/test` کد را به‌صورت `dev_otp` در همان پاسخ نشان می‌دهد. برای ارسال واقعی از سرویس [SMS.ir](https://sms.ir) (`app/auth/sms.py`)، این‌ها را در `.env` (فایل git-ignored) تنظیم کنید:

| کلید | شرح |
|---|---|
| `OTP_PROVIDER=smsir` | انتخاب تأمین‌کننده واقعی |
| `SMSIR_API_KEY` | کلید وب‌سرویس از پنل: برنامه‌نویسان → کلیدهای API (فقط در `.env`) |
| `SMSIR_VERIFY_TEMPLATE_ID` | (حالت قالب) شناسه قالب تأیید مثل «کد تایید شما: #CODE#» — اگر تنظیم شود مقدم بر خط خدماتی است و برای OTP پیشنهاد می‌شود |
| `SMSIR_VERIFY_PARAMETER` | نام پارامتر قالب؛ پیش‌فرض `CODE` |
| `SMSIR_LINE_NUMBER` | (حالت خط) شماره خط خدماتی فعال؛ متن پیام حاوی کد ارسال می‌شود |

- اگر هیچ‌کدام از قالب/خط تنظیم نشده باشد، تحویل پیامک شکست می‌خورد (fail-closed): کد صدورشده باطل می‌شود تا خنک‌سازیِ «ارسال مجدد» کاربر را قفل نکند؛ پاسخ کاربر همیشه `202` یکنواخت است و جزئیات خطا فقط در لاگ می‌رود (پاسخ هرگز تفاوت شماره‌های کارمند/بیمار را نشان نمی‌دهد).
- کلید و کد هرگز لاگ یا در پیام خطا نمایش داده نمی‌شوند؛ تماس با سرویس async است با timeout 10 ثانیه و جزئیات خطای سرویس‌دهنده leak نمی‌شود.
- برای ثبت کلید به‌صورت مخفی (بدون نمایش در ترمینال/تاریخچه): `python scripts\set_smsir_key.py` (اعتبارسنجی read-only دارد و در صورت نامعتبر بودن، چیزی ذخیره نمی‌کند).

### سامانه پیامک لوکال (حالت توسعه)

برای تست بدون پنل واقعی، `OTP_PROVIDER=fake` (پیش‌فرض) را نگه دارید؛ در `APP_ENV=development` کد OTP مستقیماً در فرم وب پر می‌شود (`dev_otp`) و پیام‌های تحویل‌شدهٔ شبیه‌سازی‌شده در صفحه «اینباکس گوشی» به نشانی:

```
http://127.0.0.1:8000/dev/sms
```

قابل مشاهده و پاک‌سازی هستند (به‌روزرسانی‌خودکار هر ۲ ثانیه). این پنل فقط وقتی فعال است که هم `APP_ENV=development|test` باشد و هم `OTP_PROVIDER=fake`؛ با انتخاب `smsir` یا در production مسیر 404 می‌شود و هیچ پیامی از آن عبور نمی‌کند. بازگشت به پیامک واقعی فقط با تغییر یک خط در `.env` (`OTP_PROVIDER=smsir`) و ری‌استارت سرور انجام می‌شود.

## ۱۰) عیب‌یابی سریع

| نشانه | علت/کار |
|---|---|
| خطای مهاجرت با پیام «duplicate links» | داده قدیمی ناسازگار؛ اسکریپت داده را تغییر نمی‌دهد و صریحاً متوقف می‌شود |
| پاسخ `429` در login | Rate limit فعال؛ بعداً تلاش کنید |
| `dev_otp` نمی‌آید | در `APP_ENV=development` فقط با `OTP_PROVIDER=fake`؛ با `smsir` کد واقعاً پیامک می‌شود |
| اینباکس لوکال 404 می‌شود | `OTP_PROVIDER` باید `fake` و `APP_ENV` باید `development`/`test` باشد |
| پیامک نمی‌رسد | با `smsir`: کلید نامعتبر/بدون اعتبار، یا نه قالب و نه خط تنظیم شده؛ کد باطل شده (درخواست مجدد بعد از خنک‌سازی) و جزئیات هرگز leak نمی‌شود |
| chat خطای ۵۰۳ | ارائه‌دهنده LLM تنظیم نشده |
